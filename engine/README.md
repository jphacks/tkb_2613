# engine

手がかりの一覧から推理ルールで結論を出す部分（`tkb_engine`）。最小削除プランナーと再診断もここに置く。

- `rules.py`：推理ルール R1（生活圏）・R2（行動時間）・R3（留守の時間）・R4（市区町村）・R5（収集地区）・R6（区画）・R7（通学先）・R8（名前）・R9（年齢）・R10（仕事）・R11（路線）・R12（生年月日）と `infer`。入出力、しきい値の場所、ルールの足し方はファイル先頭の説明を参照
- `planner.py`：消したらどうなるか（`simulate`）と危ない投稿の選び方（`plan`）。モデルは呼ばず、手がかりから消す投稿の分を除いて `infer` をかけ直す。`plan` は捜査ボードの末尾3項目を崩す投稿を最大3件選ぶ
- `links.py`：別々の投稿をつなぐ推理ルール X2（生まれた年）・X3（留守の予定）・X4（行きつけの店）・X5（勤務先・バイト先）と `link`。`infer` の最後に当てはめる。X2 は誕生日の投稿と別の投稿の「◯歳」から生まれた年を出し、R12 の誕生日と置き換える（年齢の投稿を消すと年なしに戻る）。X3 は生活圏と「来週から3泊で帰省」のような予定から家を空ける時期（`long_term_home_absence`）、X4 は2件以上の投稿に出てくる同じ店（`frequent_shop`。最寄り駅も出てくれば「◯◯駅の近く」）、X5 は「シフト」「バイト」などの話をした投稿の店・会社（`workplace`）。投稿案は `eval/demo_account/chain_posts.json`（X1 の4件のあとに投稿する。`python eval/demo_account/post_x1.py --plan chain_posts.json` で文面を確認）、モック用の手がかりは `eval/fixtures/demo_chain.json`
- `gazetteer.py`：data-prep の表（stations・postal・muni_mesh）を読み、駅名・郵便番号・住所を引き当てる

X1 は既存の生活圏（市・町・駅の順で使う）と学校の結論に、別投稿の「家から大学へ通う」という本文を加える。3種類の根拠が別投稿にあるときだけ `home_school_commute` を出し、経路と時刻は推定しない。投稿案は `eval/demo_account/x1_posts.json`。投稿前に `python eval/demo_account/post_x1.py` で文面を確認できる。

投稿を同じ日にまとめたデモでは時刻から行動時間や毎週の外出を推定しない。R2 は場所の投稿が2日以上、R3 は同じ曜日の投稿が3日以上に分かれているときだけ時刻を使う。R8 で投稿の日を誕生日とみなすのは、投稿全体が3日以上に分かれているときだけ。本文に明記された誕生日の日付はこの制限を受けない。

```python
from tkb_engine import Gazetteer, infer, plan, simulate

gaz = Gazetteer.load()  # data/processed/ が要る（make data）
conclusions = infer(clues, posts, gaz)
proposal = plan(clues, posts, gaz)  # proposal.delete / broken / before / after
what_if = simulate(clues, posts, gaz, ["at://..."])  # 選んだ投稿を消したとき
```

デモ用アカウントの手がかりに当てはめた結果は `eval/spike/run.py` で確かめる（`eval/spike/README.md`）。

## 拡張ルールの導入と確認

- `uv sync --all-packages --frozen` でバーコードの画像処理ライブラリもインストールする。
- `make data` で駅・郵便番号・市区町村メッシュ・学校の表を用意する。
  表がないときはそれに依存する推理を飛ばす。知識表だけで全ルールが動くわけではない。
- 知識表は `data-prep/manual/knowledge.json`。Dockerイメージにも同梱する。
- 推理は言語モデルを呼ばない。手がかりの抽出は従来どおりチームのモデルを使う。
- 投稿時刻を使うルールは原則3日以上に投稿が分散しているときだけ動く。同じ日への投稿でも、
  「〇歳になりました」のように本人の誕生日と明確に読める手がかりがあれば投稿日から誕生日を推定する。
- `infer` の名前の出力は `full_name` / `given_name_or_nickname`。生年月日は `birthday`。
  mainの身元カードと接続し、路線ルールはR11、生年月日はR12として残す。
- 削除提案と画面の「逃げ切り」は、診断結果の捜査ボード末尾3項目を対象にする。
  シミュレーションは実際の削除もモデル呼び出しも行わない。

知識表の指定袋価格は2025年1月31日の資料に基づく地域限定の候補照合であり、全国を網羅しない。
距離は市内の駅の平均位置による近似で、自宅からの正確な距離ではない。
八王子市の収集曜日と中央大学の時限は未確認のため空欄。未確認の時間割で大学を絞らない。
実際の学校データ取得と変換を含む確認、本番アカウントでの抽出精度の確認は別途必要。

`uv run pytest` は、手がかりの組み合わせ・削除前後・バーコード・APIの回帰を検証する。
単体テストの駅・郵便番号などは検証用の小さな表なので、
テストの成功は本番データ整備や実写真の認識成功を保証しない。

今回の追加は推理アルゴリズムと必要な知識表・抽出処理に限定する。
アカウントを作成・投稿するスクリプトや、特定アカウントの固定投稿データは同梱しない。
実際のアカウントは従来の本人ログイン後の投稿取得経路で診断する。
アカウント名に応じて固定の結論を返す処理は設けない。
