# Threads診断モデル分離の設計メモ

作成日: 2026-11-12

この文書は将来案であり、現在の本番構成や実装済み機能を表すものではない。今回のMeta `threads_basic` 審査は、モデル非依存の本人投稿表示と固定ルールセルフチェックで提出する。画像解析やGPU基盤は今回実装しない。

## 目的

- 本文だけの診断は軽量モデルで常時提供しやすくする。
- 画像診断は必要な場合だけGPU上のvLLMと画像対応モデルへ送る。
- 片方が停止しても、OAuth、本人投稿取得、一覧・詳細表示、ログアウトを止めない。
- 投稿本文、画像、トークンをログへ出さず、処理先と保持期間を公開文書に正確に反映する。

## 想定する分離

1. FastAPIがログイン本人の投稿だけを取得し、セッションメモリへ置く。
2. 本文経路は軽量なチーム管理モデルへ本文だけを送り、本文由来の観測手がかりだけを返す。
3. 画像経路は明示的に有効化された場合だけ、許可済みThreadsメディア取得仕様を別途設計してから、GPU上のvLLM画像対応モデルへ画像を送る。
4. FastAPIが両経路の観測結果を共通型へ検証し、推定エンジンへ渡す。
5. 本文モデルまたは画像モデルが停止している場合は、利用できない範囲を画面に明示し、取得済み投稿の表示とモデル非依存セルフチェックは継続する。

## 境界と安全条件

- ブラウザからモデルへ直接接続しない。
- ThreadsユーザーID、アクセストークン、Cookie、投稿IDはモデルのプロンプトへ送らない。
- 本文経路と画像経路は別々の接続先、タイムアウト、到達性確認、同時実行枠を持つ。
- モデルのリクエスト本文と応答本文をアクセスログ・アプリログへ記録しない。
- 画像バイト列とモデル入出力を永続保存しない設計を基本とし、変更する場合は実装前に保存先、目的、期限、削除方法を決めて公開文書を更新する。
- 外部のホスト型AI APIへ切り替える場合は、送信先、地域、保持条件を確認し、利用者への説明と同意を更新してから有効化する。
- 画像取得には追加のThreads APIフィールドや権限が必要かをMeta公式資料で再確認し、承認前には実装・有効化しない。

## 実装前に決める項目

- 軽量本文モデルと必要メモリ、常時稼働方法
- 画像対応モデル、GPU起動条件、停止時の縮退表示
- 各モデルの入力上限、タイムアウト、同時実行数
- モデルログを無効化または最小化する具体的設定
- 本文成功・画像失敗など部分成功時のAPI応答
- 画像取得に必要な権限とApp Reviewの追加要否
- 負荷試験、障害試験、秘密情報・投稿本文がログにないことの検証方法

この設計を実装するときは、先に `docs/api-sse-contract.md` を更新し、PythonとTypeScriptの共有型、プライバシーポリシー、利用規約、審査資料を同時に同期する。
