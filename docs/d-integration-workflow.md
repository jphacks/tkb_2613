### C02〜C05の具体案（合意前・実装未着手）

A/B/Cに持ち込むための**契約案**。下のIDと値は架空のモック例であり、Blueskyの実IDや採用済みの形式ではない。

- **C02 投稿**: `post_id` は画面・検出・推定・削除候補を結ぶIDで、クライアントは中身を解釈しない。BlueskyのAT URIを値に使う案と、短いIDからAT URIへサーバー側で対応させる案を比較して決める。どちらでも、削除時にはAT URIのリポジトリDIDが現在のセッションDIDと一致し、対象が本人の投稿であることをサーバー側で再照合する。投稿本文と画像は保存せず、セッション中だけ扱う。
- **C03 手がかり**: 既存の `type` / `value` / `confidence` / `source` に `clue_id`、`post_id` を追加する案。写真由来なら `image_index` とピクセル `region`、本文由来なら `region: null` とする案。`source` に本文を示す値が必要で、Bが名称を決める。Python/TSの型は同時に変更する。
- **C04 推定**: 画面が必要とする `key`、`value`、`status`、`confidence`、根拠の `post_id` / `clue_id` の組をCが返す案。`confidence` は検出の確からしさと推定の確からしさを混同しないよう、意味をCと決める。
- **C05 SSE**: 1投稿ごとに `post` と `clues` を流し、最後に `profile`、`plan`、`done`。一部投稿の失敗を続行するなら `error` に `post_id` と安全なエラーコードを載せる。切断・再実行・二重診断時の扱いはA/Dで決める。

```text
event: post
data: {"post":{"post_id":"p-001","created_at":"2026-10-24T00:00:00Z","text":"架空の投稿","image_count":1}}

event: clues
data: {"post_id":"p-001","clues":[{"clue_id":"c-001","post_id":"p-001","type":"station_sign","value":"架空駅","region":[10,20,90,50],"image_index":0,"confidence":0.82,"source":"vlm"}]}

event: profile
data: {"items":[{"key":"nearest_station","value":"架空駅","status":"found","confidence":0.76,"evidence":[{"post_id":"p-001","clue_id":"c-001"}]}]}

event: plan
data: {"post_ids":["p-001"],"impact":[{"key":"nearest_station","before":"found","after":"unknown"}]}

event: done
data: {"posts_seen":1,"posts_analyzed":1,"posts_failed":0}
```

本文由来の例は `region: null`、`image_index: null`、`source: "post_text"` とする**候補**。この追加値は現行スキーマでは不正なので、合意して型を両側で更新するまで実APIに送らない。画像表示用URLの作り方、投稿本文を画面へ渡す範囲、投稿IDの寿命、SSEのエラー終端条件もA/B/Cとの決定事項。

### Bluesky SDKの確認事項（実装前の参照）

- [Python SDKのQuickstart](https://atproto.blue/getting-started/quickstart/)はアプリパスワードをハードコードせず環境変数などの秘密管理で扱うことと、ログイン時のセッション作成に回数制限があるため再利用することを案内している。利用者の入力もログ・ディスクへ残さず、D06〜D07で診断ごとの再ログインを避ける。

- [投稿ガイド](https://atproto.blue/guides/posting/)では `delete_post(uri)` がAT URIを受け取る。削除しても関連する画像blob、いいね、他人の返信までは消えないと説明されている。D21〜D22でURIの所有者確認と利用者への説明を行う。

## 5. 安全上の実行ゲート

1. **本人限定**: クライアントから分析対象のDID、ハンドル、投稿URLを指定させない。セッションで認証した本人のDIDから取得する。ログイン用のハンドルは本人認証のためだけに使い、検索欄として転用しない。
2. **秘密とデータ**: アプリパスワード・鍵・Cookie値・投稿本文・写真はログやコミットに含めない。セッションと画像はメモリで扱い、有効期限とログアウトを設ける。Cookieは `HttpOnly` / `Secure` / `SameSite` を確認し、削除APIには別途CSRF対策を設ける。外部AIサービスへの送信は禁止。
3. **実削除**: シミュレーションと本番削除を明確に分ける。実投稿の削除は取り消せないため、対象と件数を示したユーザーの明示承認に加え、画面上の本人確認を経てから行う。モデルには削除権限を渡さない。
4. **費用・公開**: RunPodの読み取り疎通は既存接続先だけで行う。新規Pod起動・有料サービス利用・公開URLの有効化は、対象と費用・公開範囲を示して承認を得る。
5. **誤推定**: 観測した事実と推定を区別し、根拠投稿と確からしさを示す。アプリによる削除が既存のコピーまで消すという保証はしない。

## 6. 統合時の判定と切替

- **M1を守るための順序**: モックで画面を通す → 本人投稿取得を差し込む → Bの抽出を差し込む → Cの推定を差し込む。接続部分の不具合を1つずつ切り分ける。
- **17:00時点で実接続未完**: 実接続の作業を一度止め、モックの縦一連と中間発表を優先する。実接続の未完了を明示する。
- **19:00時点で推定未完**: 固定手がかりと根拠付き固定結果で発表し、当日実装とモックを区別する。
- **10/25午前に削除の安全条件が未完**: 実削除を無効化し、シミュレーションで削除前後を示す。
- **発表直前にGPUや回線が不安定**: 先に通した録画へ切り替え、現在動いていないものを動作中と説明しない。
- **機能を削る順序**: Threads、OAuth、OCR、実況の演出、ズーム演出、追加の集計。本人限定のログイン・根拠・削除提案・再診断の一本は維持する。

## 7. 次に必要な入力

Dが現在すぐに進められるのはC01の対象SNS部分とC02〜C07の合意、モック契約の整備である。初期ログイン方式はアプリパスワードと確認済み。実接続には、既存RunPodの接続先と鍵を秘密の共有経路で受け取ること、用意済みデモ用アカウントの管理者と認証情報の保管先を確認することが必要。これらを環境変数や秘密管理から読み取り、値を文書・チャット・ログへ転載しない。
