# プロフィール候補とプライバシー分類 v2

プロフィールの候補IDは `common/src/tkb_common/schemas.py` と `web/src/types/profile.ts` で同期する。既存16項目のうち混在していた8項目を分解し、残り8項目は維持したため候補は計25件となる。分割前のIDは候補IDとして使用しない。

カタログには25項目を定義するが、診断が返す `ProfileCandidateSet` は `home_room` を除く24項目分である。`home_room` は表示候補にも unknown セットにも含めない。

| 分割前 | 新しい候補ID |
| --- | --- |
| given_name_or_nickname | given_name / nickname |
| home_building_or_room | home_building / home_room |
| commute_station_or_line | home_nearest_station / regular_station / regular_line |
| long_term_home_absence | announced_long_absence / actual_home_absence |
| workplace | employer_name / workplace_building_candidate |
| vehicle_model_or_partial_plate | vehicle_model / partial_plate |
| partner_status_and_attributes | partner_status / partner_attributes |
| children_age_and_school | child_age / child_school |

## Claim assessment

分類は項目のカタログではなく、主張とその根拠経路ごとに付ける。`ClaimAssessment` は以下を保持する。

- `minimal_scope`: bluesky / bluesky_plus_public_web / bluesky_plus_offline。オフラインの場合は `offline_subtype` に観察・接触などの経路を書く。
- `psychological_resistance`: 1〜5。`persona_context` に本人の公開範囲やペルソナなど、評価時の文脈を記す。
- `inference_ease`: 1〜5 と `inference_ease_basis`（provisional / measured）。これは手がかり検出の `confidence` と別の指標。
- `harm_severity`: 1〜5 と具体的な `harm_scenario`、成立条件 `harm_prerequisites`、`harm_status`。

根拠がないスコアは `null` にする。成立条件がそろっていない場合は `prerequisites_unmet` を使い、現在の被害が発生しているとは表示しない。プロフィールの `confidence` は分類スコアではない。

## 推論境界

現行アプリはログイン中の本人のBluesky投稿と、そのセッションDIDのプロフィール文を取得する。診断ごとの明示同意がある場合は、公開Blueskyハンドルだけを使って公開Web上の外部SNS/ブログ/記事の候補URL・ドメイン・タイトルを検索する。本人のBlueskyプロフィールにあるURLまたは本人投稿が明示的に自分のブログ/記事/アカウントとして示すURLと検索結果が一致した場合は、その本人側リンク根拠を表示する。これは外部ページの運営者・記事著者や実世界の同一人物を確認するものではない。外部SNS/記事の本文は取得せず、プロフィール推定の根拠にも混ぜない。プロフィール文の抽出結果は自己申告として別枠表示し、限定推論に使う場合も根拠を `source=profile_text` として投稿本文とは明確に分ける。公開オープンデータの照合結果は `source=open_data` と出典抜粋で表示し、投稿根拠とは別に扱う。モックは固定の架空候補のみを使い、外部通信しない。

診断は `home_room` を除く24属性すべてに `ProfileCandidateSet` を返す。根拠のある候補がない属性も `unknown` として明示する。候補の出力条件、否定・第三者・引用の扱い、根拠のないときの unknown 条件、実装済み直接・横断推論ルールは [profile-candidate-rules.md](profile-candidate-rules.md) を正とする。候補生成は保守的であり、確定プロフィールではない。プロフィール文をアンカーに使う場合も対応する投稿根拠を要求する。単独の住所や駅から居住地や日常利用駅を決めたり、ロゴや訪問だけから勤務先を決めたりしない。候補は投稿根拠に加え、該当する場合はプロフィール文・公開Web・公開オープンデータ根拠を型付き証拠経路に含める。

各 `ProfileEvidencePath` は `provenance` を持つ。`direct_disclosure` は同じ完全経路で候補値そのものが本人の明示と型付き観測に一致する場合、`combined_inference` は関係アンカーと異なる観測など複数の根拠を結び候補値を導く場合に使う。自己申告が関係だけを示す場合（例：自宅近く、通勤習慣、子との関係）は、別投稿等の値根拠と結合した経路を `combined_inference` とする。横断経路は `residential_area`, `regular_station`, `school`, `child_age` を含む。雇用主を本文で明示し、公開Webの検証済み正式名称で同じ組織を正規化する経路は、Webが雇用関係を新たに導くわけではないため `direct_disclosure` とする。直接開示経路を候補から除外せず、推論経路としても二重計上しない。同じ候補値を支える直接経路と推論経路がある場合は、候補を一件にまとめて両方の経路を保持する。`unclassified` は互換性のための旧データ値であり、推論とみなさない。

`child_age` は、同じ子の識別的な名前と親子関係を明示した別々の本人投稿で、生年と誕生日を結べる場合に診断日時点の満年齢（0〜17歳）を候補にする。誕生日投稿の日本時間の日付から月日を取る。第三者・引用・創作、曖昧な関係や名前、正確な年齢が既に明示されたケース、未来日、うるう日の誕生日、18歳以上は棄却する。独立した有効経路が異なる年齢候補を示す場合はそれぞれを候補プールに残し、曖昧さを隠さない。値は校正済み確率ではなく証拠グレードと暫定スコアで扱う。根拠経路や危害シナリオを含む実装規則の正は [profile-candidate-rules.md](profile-candidate-rules.md) とする。FTCは氏名・住所・生年月日などの情報が子どもの身元盗用に使われると説明し、UNICEFは sharenting に伴う子どものプライバシーや共有情報の見直し・削除を説明している。これは危害の文脈であり、候補の精度を証明するものではない（[FTC](https://consumer.ftc.gov/articles/how-protect-your-child-identity-theft)、[UNICEF](https://www.unicef.org/parenting/child-care/sharenting)）。

Bluesky内の居住エリア経路は「自宅近くのX」＋別投稿の「XはY」である。雇用主を「うちの会社のX」＋「YのX」から推定する旧経路は、Xが勤務先以外の施設・事業を指しうるため停止した。Webによる勤務先名の補強は次の項の条件を維持する。

写真を使う既存の通勤駅経路は、本文に駅名を含まない本人投稿Aが「毎朝いつもの通勤駅を使う」などの習慣を明示し、別投稿Bの本文が「いつもの通勤駅から」などの利用文脈を示し、同じBの写真で高確度OCRが一意かつ完全に読んだ駅名がGazetteerに完全一致し、さらに同画像内のVLM `station_sign` 観測が同じ完全駅名・重なる矩形を示す場合だけ弱い候補にする。A/Bの投稿は別であること、駅名がAの本文に書かれていないことを要求する。B内の複数の駅名（隣駅を含む）、部分値を示す `x`、低確度、OCR/VLMどちらかのみ、矩形なし・非重複、altのみ、訪問文脈、Gazetteer未掲載駅は棄却する。駅利用習慣の本文、該当する `routine_text` 手がかり（抽出されている場合）、B本文の利用文脈、OCRとVLMの両clueを必須根拠とし、どちらの投稿を削除しても候補は消える。

写真経路とは別に、本人が駅名と自宅との関係を直接書いた投稿A（「私の自宅最寄り駅はX駅」）に同値の型付き `place_text` / `station_sign` 観測があり、別の本人投稿Bに「私は毎朝、自宅最寄りから通勤」等の反復習慣と対応する `routine_text` がある場合に限り、X駅を弱い `regular_station` 候補にする。A/Bはいずれも本人主語の非引用・非否定の投稿で、投稿時刻が有効な時差付き日時として存在し、間隔90日以内でなければならない。診断日時より未来の投稿、A/B本文またはその間にある投稿の転居・転校・転職・異動・引越し文脈、第三者の自宅を指す文、同一投稿だけの根拠は棄却する。2投稿の本文と型付き観測を一つの完全AND根拠経路にし、どちらかを除くとこの経路は消える。90日は経路の適格条件であって確率表示ではない。候補は投稿時点の通勤習慣を示し、現在も同じ駅を使う保証ではない。駅名一致だけから居住地・勤務先・学校は作らず、候補値同士から別候補を導かない。

学校は、写真からの高確度（0.85以上）のOCR/VLM `org_text` の値が大学・高校・専門学校などの接尾辞を持ち、その投稿本文にも大学・学校・キャンパスの文脈がある場合を起点にする。名称の正式性は学校一覧と照合しておらず、この接尾辞だけでは学校名の実在確認にならない。さらに別々の本人投稿に、本人の授業・講義の終わりを示す文脈と、学校祭が近いことを示す文脈がそれぞれ必要。名前のない単独ロゴ、授業だけ、学校祭だけ、訪問・見学・教職員の明示、別の学校名が出る授業・学校祭投稿は棄却する。ロゴclue・その投稿本文の学校文脈・別投稿の授業文脈・さらに別投稿の学校祭文脈を、すべて必須とする1本の経路で `weak`・confidence 0.55 の候補を出し、どれか1投稿を除けば候補は消える。これは学校への所属候補であり、学生と教職員の区別や在籍の事実を確認するものではない。パターンに合うだけで本人の学校と断定しない。

写真経路では「毎朝最寄り駅を使う」など別の位置関係を写真の駅名との橋渡しに使わない。両投稿で「いつもの通勤駅」を指す明示的な表現を要求し、駅名をすでに文章に書いている習慣投稿を写真からの特定に使わない。上記の自宅最寄り起点経路は駅名標の一致から導く写真経路ではなく、本人の直接記述と別投稿の反復習慣を結ぶ別経路である。

勤務先名には、公開Web上の組織自体の正式名称を使う追加経路を設けた。投稿Aで「勤務先はX」「勤め先はX」「うちの会社はX」のようにX自体を雇用主として明示し、別投稿Bでも同じ固有名Xに触れ、WebFactの `subject=X, relation=legal_name_of, object=Y` がそろう場合だけ、Yを弱い候補にする。「うちの会社のX」ではXが子会社・研修・施設などを指す可能性があるためWeb経路の本人アンカーとして扱わない。Xに関係する研修・イベント・施設の主催や運営情報からも勤務先を導かない。WebFactは本人の勤務関係を証明しない。同名・競合する組織名、訪問・見学文脈は棄却し、投稿を削除した後はWebFactだけで候補を残さない。実モードのWeb検索は未接続であり、現状では固定WebFactを渡した場合だけこの経路が動く。

## 仮除外の比較と候補投稿

仮除外の再評価では各属性の全 `candidate_pool` を対象にする。表示上位3件だけでなく、順位外の候補も含めて投稿を除いた後の根拠経路・順位・表示候補を計算し直す。各候補の経路内はAND、同じ値を支える複数経路はORとして扱い、除外投稿を含む経路だけを落とす。別候補が繰り上がった場合は属性が崩れた扱いにしない。候補が一つも残らなければ「この限定ルール上の支持なし」とする。これは新規推論ではなく、安全の確認でもない。

診断時の投稿候補は、候補の根拠経路が参照する診断済み投稿から最大3件を全組合せで調べる。confidence 0.5以上の完全経路を使い、まず候補が一つも残らなくなる属性数、次に失われる異なる候補値の数を優先し、その後に投稿数の少なさ、診断順を使う。順位変更だけでは属性が崩れたと数えない。属性ごとの重みは設定しない。候補が成立しない場合も、利用者は根拠に含まれる他の診断済み投稿を選んで仮比較できる。

実削除後の画面復元は `GET /api/diagnosis` が返す `deleted` を使う。診断時の投稿と手がかりの配列・番号は保持し、結論・プラン・候補セットは診断時刻 `diagnosis_at` と削除後に残るデータで再評価する。投稿が消えていれば一覧・画像・削除候補・表示中のプラン要約から外す。プロフィール候補の提案済みIDも削除済み投稿を除く。診断データはサーバーのセッションメモリに置かれ、ログアウト・セッション期限・次の診断開始で消える。
