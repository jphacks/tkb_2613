## 所見

### F-19 コンテナから資格情報を取れないことを実測で確認（情報 / OK）

設計意図どおり、コンテナからインスタンスロールの資格情報は取得できない。`AWS_*` の環境変数も 0 件で、api が AWS を直接呼ばない設計と一致する。資格情報はホストの起動スクリプトが Secrets Manager から読み、`/run` のファイルで渡す経路のみ。

**`GET /latest/meta-data/` が `401` を返したことが、IMDSv1 が拒否されている証拠**である。トークン無しの GET が 401 で弾かれる以上、IMDSv1 は通らない。同時に、コンテナからの PUT（トークン取得）は無応答で、`HopLimit: 1` によりコンテナは資格情報まで到達しない。

- 再現手順：
  1. `sudo docker exec tkb_2613-api-1 env | grep -c '^AWS_'` → `0`
  2. `sudo docker exec tkb_2613-api-1 /app/.venv/bin/python -c 'import urllib.request; print(urllib.request.urlopen("http://169.254.169.254/latest/meta-data/", timeout=5).status)'` → `401`（IMDSv1 拒否）
  3. 同 python で `PUT /latest/api/token` → `TimeoutError`（トークンは発行されない）
  4. 参考：ホストから同じ PUT を行うと `200` でトークンが返る
- 補足：コンテナはユーザー定義ネットワーク `172.27.0.0/16` 上にあり、MASQUERADE は `172.17.0.0/16` のみ対象。送信元が `172.27.0.2` のまま出るため、`HopLimit: 1` と併せて資格情報には届かない

### F-18 sshd が 22 番で待ち受けている（情報）

設計は「SSH なし」だが、ホストの sshd は `0.0.0.0:22` / `[::]:22` で起動している。SG に 22 のインバウンド規則が無いため外部からは到達できず、実害はない。「SSH なし」は SG の話であってプロセスは動いている、という表現のずれを記録する。

- 再現：`sudo ss -ltnp` で `sshd` が 22 を LISTEN
- 直し方の案：現状維持で十分。厳密にするなら `systemctl disable --now sshd`（SSM 運用に支障がないことを確認のうえ）

### F-20 リクエスト時のログ挙動が未検証（低・未検証）

起動ログに秘密情報は無く、api は `--no-access-log` でアクセスログも出さない。ただしリクエスト未送信のため、アプリ独自ログに本文・トークン・Cookie が出るかは未確認。

- 直し方の案：構造化ログにし、`authorization` / `cookie` / `password` / `app_password` をマスク。検証はダミー認証で 1 リクエスト送り `docker logs` を grep

### F-21 GPU 停止中は診断 API が恒常 503（情報）

設計どおり `model_unavailable` を返し回数も数えないため、停止中は診断が常に 503。意図的停止なので問題ではないが、「503＝異常」と読み違えないよう記録する。OCR は事前確認の対象外なので、稼働後も OCR だけ落ちていれば 503 にならず素通りする。

- 直し方の案：稼働確認に OCR のヘルスも追加する
