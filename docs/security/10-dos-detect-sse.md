# 認証不要EP・サイズ上限（カテゴリ10）

[← 目次](README.md)

- 対象: みーつけた api（FastAPI） / commit df27bac
- 実施日: 2026-11-06 / ローカル実施・破壊的操作なし
- 環境: 本番モード(:8001)。`/api/detect` に各種本文を送信

## 判定

サイズ・形式の上限は合格。負荷試験でもクラッシュ・5xx・メモリリークなし（約3,300 req/s）。レート制限は未実装（設計メモ）。SSE耐性は [12-sse.md](12-sse.md)。

| detect | 空body | 400 | 400 | 合格 |
| detect | 本番モードで画像送信 | 501（未実装） | 501 | 合格 |
| detect | 許可外 Content-Type（`text/plain`） | 415 | 415 | 合格 |
| detect | 21MiB（上限20MiB超） | 413 | 413 | 合格 |

SSE の途中切断・keep-alive・ヘッダは [12-sse.md](12-sse.md) に分離（本カテゴリは detect とサイズ上限に絞る）。

## 所見

- `/api/detect` は本文を読みながら20MiBで打ち切り413、許可外Content-Typeは415、空body400。本番モードでは実処理に入らず501。入力の大きさ・形式は適切に制限されている。
- `/api/detect` は認証不要（ログイン不要の唯一のPOST）。現状は本番501のため実害はないが、本実装時は認証・レート制限の要否を再検討する。

## 設計メモ・未測定（脆弱性ではない）

- **レート制限は未実装**（コード上、スロットリングやIP単位の制限は無い）。公開時はリバースプロキシ等でのレート制限を検討。

## 負荷試験（本気の過負荷・モックのローカルapi単一ワーカー）

実VLM/実Blueskyは対象外（共有GPU・アカウント制限を避けるため）。アプリ本体の耐性を測った。

| 試験 | 規模 | 結果 |
|---|---|---|
| `/health` スループット（ab, C製） | 50000req / 並列200 | 3,274 req/s・失敗0・p50 44ms / p99 254ms |
| ログイン連打（セッション蓄積） | 50000 POST /api/session | worker RSS 22→45MB（+約23MB ≈ 0.5KB/セッション） |
| 認証ありの診断(SSE) | 3000本 / 並列100 | 全200・全て `done` 到達・エラー0・RSS 62MB |
| 全体 | — | クラッシュ・5xx・メモリリークなし。終了後も `/health` 200 |

### 所見

- サーバ自体は高負荷に耐える。/health で約3,300 req/s、診断3000本も全完走し、落ちず・エラーを返さず・RSSも安定（ピーク約95MB）。
- 本当のDoSレバーは重い `/api/diagnose`（実モードはVLMを多数回呼ぶ）だが、ログイン必須かつ `MAX_POSTS`（既定30）で読む投稿数に上限があるため、無差別に回せない。
- セッションストアは件数上限が無いが、1件約0.5KBと軽く、5万件で+23MB。さらに実モードではセッション作成に正規ログインの成功が必要なため、認証なしのメモリ枯渇攻撃は成立しにくい。
- メモリリークは観測されず（各フェーズ後もRSSは数十MBで安定）。
- 注: Python単一プロセスのドライバでは約200 req/s で頭打ちになる（クライアント側の限界）。サーバの真のスループットは C製の `ab` で測定（127.0.0.1・keep-alive）。
- 本気の過負荷試験（多数同時接続・メモリ枯渇）は今回の範囲外（破壊的・環境依存のため実施せず）。
- SSE の途中切断・内部タスク解放は [12-sse.md](12-sse.md) を参照。
